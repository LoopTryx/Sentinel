# Phase 1 delivery checkpoints

This document records the owner's requested delivery split. The master PRD remains the authority for feature behavior and release gates. `70` and `30` are checkpoint names, not measured percentages of engineering effort. Neither checkpoint redefines R1 or R2.

## Phase 1-70 — functional preview to show the owner

The interface is intentionally plain. Every feature reads actual local state or an explicitly selected fixture; absent evidence is displayed as unavailable or partial. A demonstration fixture is never presented as active protection.

| Area | Demonstrable acceptance at 70 |
| --- | --- |
| Desktop UI and agent | Basic keyboard-usable screens for status, jobs, reports, devices, Wi-Fi, web, vault, messages, learning, and settings; live authenticated per-user agent path; cancel/progress/error states; no false green status |
| File protection | Bounded isolated scanning and inspection of selected files/folders, local verdict evidence, incomplete/skip reporting, and optional signature engine status |
| USB | Read-only device/interface inventory and manual storage scan; explicit labels for unverified storage hold and HID input gate |
| Wi-Fi and hygiene | Passive local observations, user-approved baselines, missing-permission states, and read-only security checks |
| Chrome extension | Loadable Manifest V3 harness; local fixture URL block and allow flow; service-worker restart persistence; offline warning page; native host absent state; no privileged page-to-host shortcut |
| Vault | Local encrypted vault, recovery, synthetic-credential autofill exercise with gesture and origin binding, and honest review status; valuable credentials stay out until security review |
| Mail and chat | Opt-in local analysis of open supported pages with fixture-backed rules and visible pause/partial states; live-site support claimed only after manual validation |
| Activity and learning | Bounded watcher and advisory reports, all 25 lessons with safe static interactions, privacy/settings controls |

The 70% demo must run from committed source, pass the available automated checks, and include a reproducible script. The owner will be shown the app and extension at this checkpoint.

## Phase 1-30 — release closure

1. Prove pre-access removable-storage hold and pre-input HID approval on a declared recoverable Windows hardware matrix; otherwise label the configuration unsupported and keep R1 blocked.
2. Complete transactional quarantine and restore, service recovery, installer/uninstaller, native-host registration, and policy rollback with crash/reboot tests.
3. Complete real-credential vault/autofill review, supported live mail/chat site checks, signed update validation, privacy/security review, performance and accessibility checks.
4. Pass the original R1 and R2 acceptance gates. Release labels are based on evidence, not on reaching the `70` or `30` checkpoint.

## Sequencing and evidence

Build in small committed stages: authenticated agent and worker isolation; scanner/inspector; Chrome extension harness and native bridge; passive Wi-Fi/USB/hygiene; vault and message flows; lessons/settings/activity; then the 70% demo. After that, close the 30% gates. `STATUS.md` records each stage and its limits. The user's `CRYPTIC (E:)` drive is used only for nondestructive observations and selected harmless scans; policy experiments require spare recoverable hardware and owned HID fixtures.
