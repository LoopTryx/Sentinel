# Cancellable Windows worker invocation - issue #7

5 October 2026. This is a native runtime increment on PR17, not completed worker isolation or desktop/extension integration. GLM presentation and the open glass preview assets are unchanged. Tests use ordinary harmless files and the existing test-only child executable, excluded from packaging.

## API and host sequence

`sentinel_scan::worker::scan_file_via_worker_cancellable(path: impl AsRef<Path>, worker_executable: impl AsRef<Path>, timeout: Duration, cancelled: impl FnMut() -> bool) -> Result<ScanResult, WorkerScanError>`

The existing `scan_file_via_worker(path, worker_executable, timeout)` signature remains and delegates with cancellation disabled. The executable and selected path are trusted native configuration/selection, never arbitrary browser/page arguments. Existing no-follow regular-file checks, read-only inherited handle, one-process/256 MiB Job Object, output cap, schema/report/source validation remain. Restricted token, filesystem/network denial and authenticated durable-job dispatch remain pending.

1. Authenticate/authorize the native operation and selection separately. Keep its cancellation signal under the owning job/session, not a page-supplied boolean. Pass a quick nonblocking callback, for example `|| cancelled.load(Ordering::Acquire)` from an owned atomic flag.
2. Invocation starts one cooperative monotonic timeout budget. It checks cancellation before filesystem access, after source preparation before child launch, at each Windows output loop iteration, after successful collection and immediately before returning validated evidence. Zero timeout returns TimedOut before source access. Cancellation wins when both conditions are observed at a checkpoint. No budget reset occurs at child launch.
3. During Windows collection, Cancelled follows the existing error cleanup path: request termination of this invocation's Job Object and wait/reap through the existing bounded cleanup. If cleanup cannot confirm process exit, return CleanupFailed instead of cancellation success. Closing the job also requests termination. The cleanup wait can add up to one second beyond a cooperative operation timeout; timeout is not a hard total-return latency guarantee.
4. Only `Ok(report)` supplies checked evidence. `Err(Cancelled)` and `Err(TimedOut)` supply no report, hash or checked-file result; the UI should show incomplete/cancelled or timeout with an explicit retry action. CleanupFailed means cleanup was not confirmed, not protection or completed cancellation. Suppress late results in the separately reviewed subject/job lifetime adapter. Caller cancellation after the final checkpoint is outside this synchronous return and still needs that adapter's stale-result guard.

Example: selected harmless file + configured built worker + 5-second budget + false signal -> existing partial `NoKnownFinding` report if all checks pass. Raise the owned signal after launch -> `Err(WorkerScanError::Cancelled)` after successful cleanup, no report. Missing source with signal already true -> Cancelled without source access. Missing source with zero budget and false signal -> TimedOut without source access. A valid frame from a child that does not exit is insufficient: later cancellation terminates it and returns Cancelled.

No new browser method or wire DTO is introduced. WorkerScanError is an internal native enum; downstream exhaustive matches need the new Cancelled branch. The eventual job adapter must map it to its generated cancellation state and preserve coverage/subject identity, never serialize a fabricated completed scan. No generated binding is hand-edited. This call supplies neither progress nor a shared desktop report by itself.

## Actual evidence

Nine existing Windows client process tests passed before changes. Three new tests initially failed to compile for the absent API/error variant. The first partial implementation compiled, but all three caught missing checkpoints (LaunchFailed/TimedOut instead of Cancelled); after correcting them all twelve client tests pass. Cases cover precancellation/zero budget before source access, cancellation before launch with an absent executable, cancellation at the first collector checkpoint after real launch, and a valid-frame/no-exit harmless worker cancelled during collection. Post-return source-file deletion checks inherited-handle release on Windows; tests assert bounded return under three seconds. Existing success, crash, malformed/saturated/endless output, timeout, memory/process and inherited-handle tests still pass. Strict scan/worker clippy passes.

Reproduce on supported Windows: `cargo test -p sentinel-worker --test client`, then `tools/verify.ps1`. Test helper output is never a malware-detection benchmark. No valuable files, EICAR files, E: access, Defender setting, host registration or system policy was changed.

## Remaining limits and next action

The callback cannot interrupt an OS metadata/open/CreateProcess call; cooperative checkpoints are not a hard I/O watchdog. Non-Windows development still uses the existing exit-first/blocking-output fallback and has no Windows cleanup or saturation acceptance claim. Windows containment remains resource limits and handle hygiene, not denied token/network/filesystem authority. Cleanup-failure injection, restricted parser boundary, actual authenticated job dispatch, cancellation wiring in both clients and reviewed integrated journeys remain required.
