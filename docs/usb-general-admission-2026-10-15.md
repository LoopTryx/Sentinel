# General USB input admission — implementation and acceptance record

15 October 2026. Engineer A, issue12/PR74 continuation. Owner explicitly authorizes controlled tests on this computer, overriding the repository's daily-machine test restriction for this work. This does not authorize Defender exclusions, unrelated devices/hubs, E: access, unsafe recovery or fabricated enforcement evidence.

## Product decision

The owner's final selection is authoritative: external devices must remain pending until approved in USB Guard. Do NOT preapprove the current mouse, receiver or RP2040 in a setup script. Built-in system-input exceptions are a separate safety concept, not user approval. No external approval was persisted by this increment.

The original class-based policy is too broad for a USB-only goal. The preferred candidate is pre-applied layered installation admission matching native USB HID compatibleID `USB\Class_03`, with exact-instance exceptions at the actual matching USB interface. This leaves nonUSB controls outside the matching rule; any internal USB HID interfaces still require protected, current topology enrollment. Composite HID/storage/network functions must stay separate. This is identification-based admission, not cryptographic peripheral identity or a malware verdict. Nonstandard vendor-driver input paths need separate declared support.

Microsoft documents compatible-ID denial, retroactive application to existing instances and layered instance-allow precedence. This mechanism must be active before arrivals; a popup/raw-input listener cannot retroactively prevent the first keystroke. A signed per-device input filter remains an alternative backend for dynamic packet gating, with separate WDK/signing/deployment work.

## Implemented source

Restrictive approvals cannot cross scopes. `entries_from_record(&[u8]) -> Result<Vec<Entry>,Error>` compiles bounded records without OS mutations.
- `src/policy/windows.rs`: accepts bounded V3 DenyDeviceIDs list/index and flags while preserving legacy recovery parsing. It is still an effective-registry provider, not saved-GPO enforcement evidence.
- `src/bin/sentinel-usb-policy-plan.rs`: bounded binary compiler stdin<=4072bytes -> stdout SNTPLAN1, no command arguments, no mutation or rawidentity logs. Invalid input exit2 with fixed message. Transport: magic8bytes, u16entrycount, each u8keylen/u8namelen/u32kind/u16datalen followed by key/name/data; all littleendian. Output<=32768bytes.
- `tools/usb/UsbSavedAdmissionEntry.cs`: native decoder and private saved-policy staging. Validates canonical flags/classes/USB rule, dense allow indices, exact nonempty IDs, deduplication and types; clones input before edits. Own-nonce checks, foreign-drift refusal, exact saved deletion instructions, interrupted-edit recovery. Default API refuses live DeviceInstall paths.
- `UsbAdmissionSavedGpo.cs`: private general saved-GPO editor/state reader using the same COM/STA serialized session as the qualified Ducky persistence library. It has no live general admission command.
- `UsbAdmissionPreflight.cs`: bounded read-only full topology/USB-interface evidence; instance IDs remain in memory. `EvaluateUsbHid` selects actual USB subjects whose native compatibleIDs include exact USB\Class_03, not inferred HID children. Internal candidates versus external approval needs stay separate. Topology token is canonical lowercase SHA256. Collection is soft-bounded and native calls need an external process timeout.
- `UsbAdmissionJournal.cs`: protected admin/SYSTEM-only durable operation intent, exclusive file/dir pins, lock-serialized access, scope3 validation, exact flush/readback, corrupt/active/stale-clear refusal and deadline/backward-clock recovery semantics. Integrity checksum does not authenticate callers; deployment must keep trusted ancestor pins and authenticate native authority.
- Native qualification fixtures exercise the above under bounded SYSTEM jobs and independent timed recovery. They accept no arbitrary real-device identifiers.

## Persistent enrollment storage — 16 October follow-up

`tools/usb/UsbEnrollmentConfig.cs` implements persistent enrollment separately from `UsbAdmissionJournal`. It does not change device policy or authenticate approval. Its immutable snapshot contains a canonical account `OwnerSid`, monotonically advancing generation, `InternalSafety` and `ApprovedExternal` arrays. Both arrays remain separate; no attached device is silently approved. The combined list is bounded to 32 exact IDs and 4072 policy-equivalent bytes. IDs and owner identity are stored only in protected local files, never diagnostic output.

Native integration contract: create the store only inside a validated admin/SYSTEM-only directory while retaining trusted ancestor pins. The store retains its own final-directory pin and exclusive lock. `ReadCommitted()` and `ReadPending()` return snapshots; `Commit(expectedGeneration,next)` requires exactly the next generation, unchanged owner, and no existing proposal. It writes `enrollment.pending`, flushes and verifies all bytes before atomic replacement of `enrollment.bin`. Pending proposals never become approvals on startup. A valid uncommitted proposal may be discarded only with matching committed/pending generations through `DiscardPending`; malformed files refuse automatic repair. Atomic visibility is not a claim of storage-controller power-loss immunity.

Before a real commit, the native authority must verify Windows Hello against the configured owner and revalidate current native device/topology evidence. This storage API must never be exposed directly to the renderer or treat the Hello qualification receipt as authorization. Policy activation, operation-journal recovery and enrollment persistence still require a reviewed coordinated transaction; committing preference alone cannot claim a blocked or allowed input path.

Executed evidence: `tools/usb/tests/build-usb-enrollment-config-test.ps1` built both Framework executables and passed pure validation. Final reviewed protected native fixture exited 0; `HKLM\SOFTWARE\Sentinel\UsbEnrollmentConfigQualification` reported `State=complete, Stage=0`. Tests cover invalid/non-account owner SIDs, owner replacement refusal, duplicate/invalid IDs, exact capacity and overflow, immutable snapshots, corrupt committed state, exclusive access, stale generations, half-written staging, pre-replace interruption, post-replace lost response, reopen and explicit valid-stage discard. The fixture used only synthetic identities in a pinned protected test directory, cleaned exact test files and made no DeviceInstall changes. Independent review found no concrete blocker within this isolated storage qualification scope.

## General admission transaction and native authority — 16 October

Implemented an initial-only coordinator in `UsbAdmissionTransaction.cs`: immutable digest binds owner/configuration generation, exact scope-3 policy, topology, nonce and UTC deadline. It refuses active policy/journals and deadline extension. It persists intent and verifies independent recovery before applying, verifies policy before committing enrollment, and retains uncertain state for recovery. Restoration requires producer quiescence and fresh restored-state verification before retiring recovery and clearing intent. Boundary tests inject failures before and after every apply/recovery operation, including lost replies, clock rollback, expiry and configuration/topology drift. These are coordinator tests with synthetic native seams, not Windows enforcement evidence. Active approval updates/renewal require a versioned baseline transaction and remain explicitly refused.

`UsbAdmissionAuthorization.cs` and `UsbAdmissionNativeAuthority.cs` provide the actual same-process native Hello-to-request adapter. They require the foreground native HWND, an active local Windows session whose account matches the elevated token and configured owner, and a single-use 30-second proof bound to the request. Alternate-administrator elevation cannot become owner approval. The native adapter recollects inventory, requires every internal safety candidate, rejects external-to-safety reassignment and refuses stale/absent selections. Pure tests cover replay, expiry, mismatch, missing safety entries and classification/selection changes. The updated real native qualification succeeded; categorical `UsbAdmissionOwnerQualification.State=verified` includes immediate replay refusal. It made no USB changes.

A real read-only saved/effective policy survey found a migration dependency on this machine: saved restrictions root absent; effective root present with two valid known switches, zero list entries, no unknown values/subkeys and a legacy Sentinel marker. Known switches do not match. This is leftover state, not proof of ownership or current blocking. No values were removed. Migration must authenticate protected historical receipts and exact task actions, establish quiescence and preserve foreign policy; merely observing the marker is insufficient.

The source-only `UsbAdmissionMachineGpo.cs` candidate edits the actual canonical owned delta and emits release deletion instructions, while preserving legacy/foreign conflicts. Its default live entry is compile-disabled. Disposable HKCU tests passed. Independent recovery worker authentication, durable cleanup stages, exact legacy migration and final repeat-operation cleanup must be connected and verified before enabling that entry. Neither this source nor coordinator test success indicates installed general USB protection.
